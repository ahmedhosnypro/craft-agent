## 2. OpenAI Codex on GitHub — three distinct official paths

As of 2026-10, "Codex on GitHub" is three separate integrations with different auth, billing, and execution models.

### 2a. Plan-linked GitHub integration (ChatGPT Codex Connector GitHub App)

- GitHub App: `chatgpt-codex-connector` ("Bring ChatGPT and Codex to your GitHub repositories"), owned by the `openai` org, created 2025-02-14. Verified via `gh api /apps/chatgpt-codex-connector`. Source: https://github.com/apps/chatgpt-codex-connector
- Subscribed events: check_run, check_suite, commit_comment, issues, issue_comment, pull_request, pull_request_review, pull_request_review_comment, pull_request_review_thread, repository, status, sub_issues. (Verified via the same API call.) Note: issues/issue_comment events exist, but the *documented* trigger surface is PR comments (below).
- App permissions: actions:write, checks:read, contents:write, emails:read, issues:write, metadata:read, pull_requests:write, statuses:read, workflows:write. Source: same API call.
- Install path: user connects GitHub to Codex in ChatGPT/Codex settings (Connectors/Integrations) or installs the app from the app page for an org, granting all-repo or selected-repo access. Repo must then be connected + code review enabled in Codex settings (https://app.chatgpt.com/settings/code-review). Source: https://learn.chatgpt.com/docs/third-party/github
- Documented triggers (all in *pull request comments*):
  - `@codex review` — posts a standard GitHub code review; flags only P0/P1 issues. Optional focus text: `@codex review for issues in the database migration`. Source: https://learn.chatgpt.com/docs/third-party/github
  - `@codex security review` — Security Review (research preview), posts security findings + Security Report tab. Source: same page.
  - `@codex fix the P1 issue` (or any non-review text, e.g. `@codex fix the CI failures`) — starts a "legacy cloud chat" with the PR as context and can push a fix back to the branch when it has permission. Source: same page.
  - Automatic review: per-repo toggle "Automatic review" + "Review trigger" in Codex settings; no mention needed. Auto security review runs alongside code review. Source: same page.
- No issue-assignment flow is documented in current official docs: the search hits and docs agree the PR-comment surface is the documented trigger (the app's issue events remain for other purposes). Marked: NOT VERIFIED as a current documented trigger.
- Configuration: `AGENTS.md` (repo root + nested; `## Code Review Rules` section customizes reviews; root + nearest-file merge, `AGENTS.override.md` precedence, 32 KiB default `project_doc_max_bytes` cap). Source: https://learn.chatgpt.com/docs/agent-configuration/agents-md and .../docs/third-party/github

Task flow: container created, repo checked out at branch/SHA, setup script runs (with internet), then agent phase with internet off by default behind an HTTP/HTTPS proxy; secrets decrypted only for setup scripts and removed before the agent phase; container state cached up to 12h. Source: https://learn.chatgpt.com/docs/environments/cloud-environment

- Billing: ChatGPT-plan-linked. Sources: https://learn.chatgpt.com/docs/pricing

### 2b. OpenAI Codex GitHub Action — `openai/codex-action@v1` (the BYOK path)

- Official repo: https://github.com/openai/codex-action (Apache-2.0, actively maintained, pushed 2026-10-09). Official docs page: https://learn.chatgpt.com/docs/github-action ("Trigger Codex actions from GitHub Events").
- What it does: installs the Codex CLI on *your* Actions runner, starts a secure local proxy to the Responses API, and runs `codex exec` under permissions you specify. You keep control of runner, triggers, and privileges. Source: action README + docs page.
- Auth/billing: pure BYOK — `openai-api-key` input from a repo secret (`OPENAI_API_KEY`, or `AZURE_OPENAI_API_KEY` + `responses-api-endpoint` for Azure OpenAI, e.g. `https://<project>.openai.azure.com/openai/v1/responses`). Billed as API usage; no ChatGPT plan required. Source: action README (Azure section).
- Key inputs: `openai-api-key`, `prompt` XOR `prompt-file`, `output-file`, `working-directory` (→ `codex exec --cd`), `permission-profile` (`:workspace` / `:read-only`, beta, needs CLI ≥0.138.0) XOR legacy `sandbox` (`workspace-write`/`read-only`/`danger-full-access`), `codex-version`, `codex-args` (JSON array or shell string), `output-schema`/`output-schema-file`, `model`, `effort`, `codex-home`, `safety-strategy` (default `drop-sudo`; also `unprivileged-user`, `read-only`, `unsafe` — Windows only supports `unsafe`), `codex-user`, `allow-users`, `allow-bots`, `allow-bot-users`, `responses-api-endpoint`. Output: `final-message`. Source: action README Inputs/Outputs tables.
- Trigger gating: by default only users with write access can trigger; `allow-users`/`allow-bots` extend to trusted accounts. Source: action README + docs page.
- Security model (notable for our project): `drop-sudo` revokes sudo + root-owned service sockets (incl. Docker socket ACL), starts Codex with `no_new_privs`, empty capability sets; enables unprivileged user namespaces on hosted Linux runners (AppArmor workaround for bubblewrap); protected runs reject `codex-args` overrides that change permissions/trust/providers/config profiles. Source: action README (Safety Strategy, Permission profiles).
- Canonical auto-fix pattern (from official `codex exec` docs): two-job split — `generate_fix` job with only `contents: read` runs Codex and uploads `codex.patch` as an artifact; a separate `open_pr` job with `contents: write` + `pull-requests: write` (but NO API key) applies the patch and opens a PR as `github-actions[bot]`. Trigger: `on: workflow_run` for a failed CI workflow. Source: https://learn.chatgpt.com/docs/non-interactive-mode (Codex auto-fix on CI failure example).
- Official docs explicitly steer CI users to the action: "For GitHub Actions, use the Codex GitHub Action instead of installing and authenticating the CLI yourself… Do not set OPENAI_API_KEY or CODEX_API_KEY as a job-level environment variable in workflows that check out or run repository-controlled code." Source: same page.
- PR-review bot example: checkout `refs/pull/N/merge` with `persist-credentials: false`, pre-fetch base/head refs, run the action with a review prompt, post `final-message` via `actions/github-script` in a second job with `pull-requests: write`. Sources: action README + https://learn.chatgpt.com/docs/github-action
- Extra repo for local testing of the cloud image: openai/codex-universal (Dockerfile for Codex's default cloud container image). Source: https://learn.chatgpt.com/docs/environments/cloud-environment

## 3. Codex CLI headless/exec mode for CI (verified flags)

Source for all flags: https://learn.chatgpt.com/docs/non-interactive-mode (official `codex exec` docs; flag-level reference at learn.chatgpt.com/docs/developer-commands#cli-codex-exec).

- Invocation: `codex exec "prompt"`. Progress streams to stderr; only the final agent message goes to stdout. Piped stdin becomes context when a prompt arg is given (prompt-plus-stdin); `codex exec -` forces stdin as the entire prompt.
- Sandbox: default `read-only`. `--sandbox workspace-write` for edits; `--sandbox danger-full-access` only in controlled environments. `--full-auto` is a DEPRECATED compatibility flag that prints a warning — do not use in new scripts.
- Permission profiles (newer, beta, CLI ≥0.138.0): selected via `default_permissions`/config instead of `--sandbox`; built-ins `:workspace` and `:read-only`; do not compose with `--sandbox` or `--full-auto`.
- Machine-readable output: `--json` → JSON Lines event stream on stdout. Event types: `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*` (agent messages, reasoning, command executions, file changes, MCP tool calls, web searches, plan updates), `error`. `turn.completed` carries a `usage` object (input/cached/output/reasoning tokens).
- Final message to file: `-o <path>` / `--output-last-message <path>` (still prints to stdout).
- Structured output: `--output-schema <schema.json>` forces the final response to conform to a JSON Schema — designed for automated pipelines.
- Session hygiene: `--ephemeral` (no session rollout files); `codex exec resume --last` / `codex exec resume <SESSION_ID>` for multi-stage pipelines; `--skip-git-repo-check` (Codex otherwise requires a git repo); `--ignore-user-config` (skip $CODEX_HOME/config.toml); `--ignore-rules` (skip user/project execpolicy `.rules`).
- Working dir: `--cd` (what codex-action's `working-directory` maps to). MCP: an enabled MCP server with `required = true` that fails to init makes `codex exec` exit with an error.
- Auth in automation: `CODEX_API_KEY` env var, ideally inline for a single invocation (`CODEX_API_KEY=<key> codex exec --json …`); works with `codex exec`, `codex review`, the TS SDK, and `codex exec-server --remote`. Never a job-level env when untrusted repo code runs in the same job. ChatGPT-account auth in CI/CD exists (seeded `~/.codex/auth.json`, advanced) but is explicitly NOT for public/OSS repos. Source: same page.
- Security guidance: prefer the GitHub Action (proxy + drop-sudo) over raw CLI in workflows; for privileged operations expose a narrow local MCP server instead of broad runner access. Sources: https://learn.chatgpt.com/docs/non-interactive-mode + https://github.com/openai/codex-action/blob/main/docs/security.md
- Rust note for us: `codex` itself is a Rust workspace in openai/codex (codex-rs), and the CLI can also be driven via the app-server protocol / TypeScript SDK (`@openai/codex-sdk`) — an alternative to shelling out. Sources: https://github.com/openai/codex ; https://learn.chatgpt.com/docs/codex-sdk

## 4. GitHub Copilot cloud agent (platform-native option)

The old "Copilot coding agent" docs now live under "Copilot cloud agent" (redirects verified: /copilot/concepts/agents/coding-agent → cloud-agent).

- How it runs: each task gets an ephemeral development environment powered by GitHub Actions (GitHub-hosted by default; can be upgraded). The agent explores code, edits, runs tests/linters, then creates a branch, commits, pushes, and opens a PR; you review, request refinements, or continue yourself. Sources: https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github ; https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment
- Environment customization: `.github/workflows/copilot-setup-steps.yml` — a normal workflow file with a single `copilot-setup-steps` job that runs before the agent starts (preinstall tools/deps, e.g. Rust toolchain for cargo test/clippy). Options: larger GitHub-hosted runners, self-hosted runners (code review: ARC-managed only, Ubuntu x64; firewall must allow api.githubcopilot.com, uploads.github.com, user-images.githubusercontent.com), Windows environment, Git LFS. Org owners can set a default runner type and block repo overrides. Sources: customize-the-agent-environment + set-up-copilot/configure-runners.
- Enablement: disabled by default. Enterprise: AI Controls → global policy for Copilot cloud agent (selected orgs; REST API supports custom-property org selection); org-level on/off; repo-level blocks; individuals enable in account settings (paid plans: Pro, Pro+, Max, Business, Enterprise). Third-party MCP servers are a separate policy. Source: https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/enable-copilot-cloud-agent
- Triggers: assign an issue to Copilot (right sidebar Assignees, with optional prompt), start from the Agents tab (github.com/copilot/agents) or a chat, PR comments, mobile, VS Code; security campaigns can assign code-scanning alerts to it; Copilot Automations run it on a schedule or on repo events (e.g. issue opened) — automations currently limited to eligible private/internal repos. Sources: copilot-on-github.md ; agent-management.md ; cloud-agent/about-automations.
- Steering/review UX: live session logs, mid-session steering input (consumes AI credits), open session in VS Code or Copilot CLI, review + merge from PR. Source: https://docs.github.com/en/copilot/concepts/agents/cloud-agent/agent-management
- Custom instructions: `.github/copilot-instructions.md` (repo-wide), `.github/instructions/NAME.instructions.md` (path-specific); agents read the nearest `AGENTS.md` anywhere in the repo, or a root `CLAUDE.md`/`GEMINI.md`. Cloud agent can generate a copilot-instructions.md for you. Sources: https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions ; data/reusables/copilot/custom-instructions-agents.md
- Extensions: custom agents (task-specific system prompts, e.g. test-writer), agent skills, MCP servers, hooks, secrets/variables, firewall rules. Sources: cloud-agent/about-custom-agents ; customize-cloud-agent pages.
- Billing: AI credits — 1 credit = $0.01 USD. Included monthly credits per user: Pro 1,000; Pro+ 3,900; Max 10,000; Business 1,900; Enterprise 3,900 (pooled at billing-entity level; additional usage on by default, can be capped/blocked). Cloud agent, chat, Copilot CLI, Spark, and third-party coding agents all consume AI credits; code completions/next-edit suggestions remain unlimited. Sources: https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing ; github/docs data/variables/copilot.yml.
- What it cannot do (constraints worth copying): no secrets in the agent environment except explicitly configured ones; review-and-approve stays human (logs do not replace review/testing); agent PRs are marked and can be excluded from required-review counts; needs the setup-steps file for non-default toolchains. Sources: copilot-on-github.md ; configure-secrets-and-variables.
- GitHub Agentic Workflows (gh-aw) — GitHub's own Actions-native agent runner, preview: markdown workflow (YAML frontmatter: `on`, `permissions`, `network`, `tools`, `safe-outputs`, `engine`) compiled via `gh aw compile` into a hardened `.lock.yml` Actions workflow. Engines: Copilot (default), Claude Code, OpenAI Codex, Google Gemini (+Agy/Pi experimental; custom engines; Azure BYOK). Security guardrails: read-only-by-default GITHUB_TOKEN, write actions only via validated `safe-outputs`, secrets isolated in downstream jobs, agentic threat detection, firewalled Actions containers, role-based access. ## 7. Implications for our BYOK action project (storytold)

1. Crowded space — differentiate on verification-first, Rust-native, org-tailored. Official options now cover review (Connector), assign-and-implement (Copilot/3p agents), CI auto-fix (codex-action), and markdown automations (gh-aw). Pure "agent on GitHub Actions" is no longer novel. Our differentiators from the verified gaps: (a) Rust-first toolchain (cargo test/clippy/rustfmt as first-class verification gates), (b) multi-model BYOK with explicit budget caps, (c) storytold-org conventions (~22 pure-Rust apps: one AGENTS.md + shared action), (d) patch-artifact isolation done by default.
2. Reuse the two-job security pattern. The official auto-fix architecture (agent job with contents:read only + no push; PR job with write + no API key; patch passed as artifact) is the proven blast-radius model — adopt it as our default, not as an option. Source: https://learn.chatgpt.com/docs/non-interactive-mode
3. Never pass the API key as a job-level env var; if we shell out to `codex exec`, prefer the action's proxy approach (key visible only to proxy) or inline per-invocation CODEX_API_KEY, and replicate drop-sudo-style privilege stripping on Linux runners. Sources: codex-action README + non-interactive docs.
4. Drive codex exec, don't build our own agent loop, if Codex is the engine: `--json` JSONL events + `--output-schema` + `-o final.txt` give a stable contract; `--sandbox workspace-write` (not deprecated `--full-auto`); pin `codex-version`; permission profiles (`:workspace`) are the future-proof mode (CLI ≥0.138.0).
5. Trigger design: the ecosystem converged on explicit, permissioned triggers — `@codex review` mentions (write-access users only), issue assignment, or labeled/automatic events. Our action should default to: issue-comment command (e.g. `/agent ...`) restricted to users with write access (mirror codex-action's `allow-users`/`allow-bots` gating), plus an opt-in label/assignment trigger. Avoid auto-running on every PR: automatic review costs credits/minutes and OpenAI flags only P0/P1 to stay high-signal — copy that signal discipline.
6. AGENTS.md is the config lingua franca: Codex reads it (global + nearest-file, 32 KiB cap), Copilot reads nearest AGENTS.md, gh-aw imports "Copilot Agent Files". Ship a storytold org-level AGENTS.md convention + per-repo overrides; keep it small (usage-limit docs explicitly advise smaller AGENTS.md to conserve credits).
7. Complement vs substitute: for our own repos, Copilot cloud agent/gh-aw can substitute most issue→PR flows *if* we pay for Copilot plans — but BYOK remains the only path with model/provider freedom, per-key budget control, self-hosted-runner privacy, and zero subscription. For OSS consumers of our action, BYOK is the only universally installable option (no ChatGPT/Copilot plan needed). Position our action as BYOK + Rust-verification-first; interoperate with (not fight) AGENTS.md and, optionally, the `codex` engine.
8. Cost control is a first-class feature expectation: gh-aw's `max-ai-credits` (default 1,000 AIC = $10) per run and Codex's usage dashboard show users want caps — build per-run token/credit budgets and a usage summary comment into v1.
9. Funding angle: apply to the Codex for Open Source fund (API credits + 6 months ChatGPT Pro) — it explicitly funds "projects that use Codex in pull request review, maintainer automation, release workflows". Source: https://developers.openai.com/community/codex-for-oss
10. Competitive watch items: gh-aw is MIT-licensed and Actions-native — before building, decide whether our project is (a) a gh-aw engine/workflow pack, (b) a standalone action wrapping `codex exec`/API with Rust verification, or (c) a Rust binary + action that is engine-agnostic (OpenAI, Azure, Anthropic-compatible endpoints). Option (c) + Rust-first verification gates is the least-overlapping, most-OSS-friendly niche.
