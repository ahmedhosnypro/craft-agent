# grok-build — xAI/SpaceXAI "Grok Build": a production-grade Rust agent engine (CLI/TUI)

Exploration of /home/ahmed/Projects/grok-build for the storytold agentic GitHub Action project (slug ex7-grok-build). Every claim cites a real file in that tree.

## 1. What it is

- **Grok Build** is "SpaceXAI's terminal-based AI coding agent" shipping as the `grok` binary: a full-screen TUI that understands a codebase, edits files, executes shell commands, searches the web, and manages long-running tasks — interactively, headlessly for scripting/CI, or embedded in editors via the Agent Client Protocol (ACP). Source: README.md lines 13-17.
- The repository is the Rust source of the `grok` CLI/TUI plus its agent runtime, "synced periodically from the SpaceXAI monorepo" (README.md lines 31-32). First-party code is Apache-2.0; external contributions are NOT accepted (README.md lines 127-130; CONTRIBUTING.md).
- Build artifact is named `xai-grok-pager` and installs as `grok`; composition-root package is `crates/codegen/xai-grok-pager-bin` (README.md lines 76-83; crates/codegen/xai-grok-pager-bin/Cargo.toml `[[bin]] name = "xai-grok-pager"`).
- Root Cargo.toml is auto-generated and read-only ("Auto-generated workspace root. Prefer editing per-crate Cargo.toml files", Cargo.toml line 1); ~100 workspace members under crates/codegen, crates/common, crates/build, prod/mc, third_party (Cargo.toml lines 8-111).
- Toolchain pinned to Rust 1.94.0 with rustfmt+clippy (rust-toolchain.toml); DotSlash required for the hermetic `bin/protoc` stub that downloads pinned protoc 29.3 per platform (README.md lines 56-73; bin/protoc).
- A 27-chapter user guide ships in-tree at crates/codegen/xai-grok-pager/docs/user-guide/ — headless mode, agent mode (ACP), custom models, sandbox, permissions, skills, hooks, MCP (README.md lines 85-93; ls of that dir).

## 3. Architecture (crates and roles)

Request path (pager -> shell -> sampler -> provider):

- `crates/codegen/xai-grok-pager-bin` — composition-root binary; wires the pager library, shell runtime, login, sandbox, update, telemetry, crash handler (crates/codegen/xai-grok-pager-bin/Cargo.toml).
- `crates/codegen/xai-grok-pager` — the TUI (scrollback, prompt, modals, rendering) plus headless single-turn mode: "Runs the agent in-process and drives the ACP lifecycle (init, auth, session, prompt). Streams to stdout and exits via CancellationToken" (src/headless.rs lines 1-4); all CLI definitions live in src/app/cli.rs.
- `crates/codegen/xai-grok-shell` — agent runtime + leader/stdio/headless entry points (README.md line 101); `run_headless`/`run_leader` in src/agent/app.rs; the agent loop lives in `MvpAgent` (src/agent/mvp_agent/, e.g. agent_runtime.rs, session_lifecycle.rs, turn_end.rs, subagent_spawn.rs).
- `crates/codegen/xai-grok-agent` — "Agent builder, definition parsing, and system prompt assembly": an Agent bundles tools, system prompt, reminder policy, compaction policy, model config (src/lib.rs lines 1-24). Built-in agent types: GrokBuild, GrokBuildConcise, GrokBuildPlan(±subagents), GrokBuildAskUser, Codex, Opencode, GeneralPurpose, Explore, Plan, BrowserUse, GrokBuildOrchestrator (src/config.rs `BuiltinAgentName::definition`).
- `crates/codegen/xai-chat-state` — actor-based conversation state in a dedicated tokio task: conversation Vec<ConversationItem>, sampling config, prompt_index, token totals (src/lib.rs architecture diagram).
- `crates/codegen/xai-grok-sampler` — "Actor-based sampling/inference layer for xAI grok (HTTP streaming + retry, no shell coupling)"; layered API: SamplingClient raw chunks -> stream transforms -> SamplerHandle actor managing concurrent requests with retry/cancellation (src/lib.rs lines 1-16). Speaks `/chat/completions`, `/responses`, `/messages` (src/client.rs lines 6-7).
- `crates/codegen/xai-grok-sampling-types` — wire types: `ApiBackend` enum { ChatCompletions (default), Responses, Messages } (src/types.rs line 1046) plus per-backend facts (supports_native_schema, forwards_prompt_cache_key, default_max_request_bytes 50 MiB vs 30 MB).
- `crates/codegen/xai-grok-models` — default model IDs embedded at compile time from default_models.json (default `grok-4.6`, context_window 500000, api_backend "responses"); resolution order CLI flag > ENV > config.toml > remote settings > these defaults (src/lib.rs lines 1-7; default_models.json).

Tools and host layer:

- `crates/codegen/xai-grok-tools` — tool implementations in namespaces under src/implementations/: `grok_build` (native set), `codex` (openai/codex ports), `opencode` (sst/opencode ports), plus `grok_build_concise` and `grok_build_hashline` (hashline-anchored read/edit/grep) variants (src/implementations/mod.rs).

- `crates/common/xai-tool-protocol` + `xai-tool-types` — ToolId wire identity, canonical tool-description and capability types shared across tool sources.
- `crates/codegen/xai-grok-tools-api` — protobuf gRPC service GrokToolsService (ExecuteTool, ExecuteToolStream, ListTools, GetToolInfo, FinalizeToolConfigRequest) in package `xai.grok.tools.v1` (proto/grok-tools.proto lines 8-35) so tools can run out-of-process.

- `crates/codegen/xai-grok-shell/src/leader` — single-leader-per-machine IPC: one leader process owns agent state while TUI/IDE/headless clients talk ACP over a Unix socket at ~/.grok/leader.sock (src/leader/mod.rs module doc + diagram).

## 4. Agent capabilities

**Tools exposed to the model** (ls crates/codegen/xai-grok-tools/src/implementations/grok_build/): run_terminal_cmd (bash, foreground + background tasks), read_file, search_replace, grep, list_dir, task (subagent spawn; aliases Task/spawn_subagent, task/mod.rs line 196), task_output, kill_task, todo, update_goal, ask_user_question, enter_plan_mode/exit_plan_mode, web_search, web_fetch, lsp, monitor, scheduler, workflow, image_gen/image_edit, video_gen, send_feedback, send_subagent_message, storage.

- Tool output caps: DEFAULT_TOOL_OUTPUT_BYTES = 40_000 per result, DEFAULT_TOOL_OUTPUT_CHARS = 20_000 for bash (xai-grok-tools/src/lib.rs lines 9-16).
- Tool gating DSL: tools declare requirements over sibling tools/params, e.g. bash requires BackgroundTaskAction + KillTaskAction tool kinds when backgrounding is enabled (bash/mod.rs Expr::And/if_params, lines 1490-1500).
- Three complete toolset namespaces; `agent_type` selects prompt + tools: native grok_build, codex ports (apply_patch, read_file, grep_files, list_dir), opencode ports (read/edit/write/glob/grep/skill/todowrite) (implementations/{codex,opencode}/mod.rs).

**Sandboxing & permissions:**

- OS sandbox is off by default; profiles: workspace (read everywhere, write CWD + ~/.grok + /tmp), devbox, read-only, strict (most restrictive; child network blocked). Kernel-enforced Landlock (Linux) / Seatbelt (macOS) via nono; child-process network blocked by seccomp on Linux only. Selected via `--sandbox <profile>` or sandbox.toml (docs/user-guide/18-sandbox.md lines 9-36).
- Permission modes: default(ask), acceptEdits, plan, auto, dontAsk, bypassPermissions (a.k.a. always-approve / `--yolo`); allow/ask/deny glob rules like `Bash(rm*)`, `Read(src/**)`, `WebFetch(domain:...)`; deny rules take precedence; hooks still apply in always-approve (docs/user-guide/22-permissions-and-safety.md lines 10-72; 14-headless-mode.md lines 84-100).
- Hooks: JSON files in ~/.grok/hooks/ and <repo>/.grok/hooks/; events session_start, pre_tool_use, post_tool_use, user_prompt_submit, stop/subagent_stop, notification, session_end; pre_tool_use hooks can allow/ask/deny and rewrite tool input via `updatedInput`; fail-open by default (xai-grok-hooks/src/lib.rs lines 1-28).

**Sessions & context management:**

- Sessions under GROK_HOME (default ~/.grok); resume by id or title (-r), continue (-c), fork (--fork-session); worktree isolation via -w/--worktree; `grok clone` fetches into a Grove content store with a projected working tree (docs 14-headless-mode.md; 27-grok-clone.md).
- Auto-compaction at a per-model threshold percent (80% in default_models.json); compaction-core behind CompactionItem/ItemTokenCounter/CompactionSampler trait seams (xai-grok-compaction/src/lib.rs).
- Per-prompt rewind checkpoints: FS snapshot + hunk delta + git HEAD/index (xai-grok-workspace/src/session/checkpoint.rs).
- Subagents: `task` tool -> SubagentBackend -> coordinator actor; children get their own context windows; resolution precedence explicit > role > persona > parent; depth capped via MaxSubagentDepth; built-in child types general-purpose/explore/plan (task/mod.rs lines 1-25; xai-grok-subagent-resolution/src/lib.rs).

**Modes and CLI entry points** (xai-grok-pager/src/app/cli.rs `Command` enum; AgentArgs/AgentCmd lines 255-339):

- Interactive TUI: bare `grok`.
- One-shot headless: `grok -p "prompt"` (or --prompt-json/--prompt-file); --output-format plain|json|streaming-json|streaming-messages-json; --tools allowlist / --disallowed-tools denylist (supports `Agent(explore)` entries); --max-turns; --allow/--deny permission rules; --yolo; -m/--model; --reasoning-effort; --sandbox; exit codes 0 success / 1 error / 130 SIGINT / 143 SIGTERM (docs 14-headless-mode.md lines 19-47, 559-567).
- ACP server: `grok agent stdio` (JSON-RPC over stdio; IDE path) and `grok agent serve --bind 127.0.0.1:2419 --secret` (WebSocket; GROK_AGENT_SECRET env) — "Grok's hosted cloud sandboxes do not run `grok agent serve`" (docs 15-agent-mode.md lines 7-13, 74-82).
- Relay mode: `grok agent headless --grok-ws-url wss://...` connects the agent to a WebSocket relay for remote control (docs 15 lines 84-89).
- Leader mode: a shared leader process owns agent state so multiple clients share one backend; clients connect-or-spawn via a Unix socket (xai-grok-shell/src/leader/mod.rs; cli.rs AgentCmd::Leader).
- Management subcommands: login (--oauth / --device-auth for headless), logout, models, sessions, usage, inspect (--json config discovery), doctor, mcp, plugin, memory, worktree, export (Markdown transcript), trace, update (stable/alpha/enterprise channels), wrap (OSC-52 clipboard PTY wrapper), completions, workspace (hidden Computer Hub exposure, GROK_WORKSPACE_COMMAND=1), dashboard (cli.rs lines 14-155).

## 8. Reusable patterns for a Rust agentic GitHub Action engine

1. Crate topology — small single-purpose crates with trait seams:
   - The LLM client (xai-grok-sampler) is fully decoupled from the shell ("no shell coupling", src/lib.rs) — exactly what an Action engine wants: an inference crate with zero TUI/desktop deps.
   - compaction-core behind CompactionItem/ItemTokenCounter/CompactionSampler seams so summarization works for any conversation type (xai-grok-compaction/src/lib.rs).
   - tool-runtime is the single home of the Tool trait; every tool source (native, codex, opencode, MCP) adapts to it (xai-tool-runtime/src/lib.rs lines 1-15) — implement a tool once, drive it from CLI, ACP server, or Action alike.
2. Tool design — the `Tool` trait pattern (xai-tool-runtime/src/tool.rs): typed Args via schemars::JsonSchema (schema derived, never hand-written), typed Output with model-facing content blocks, streaming ToolStream invariant (many Progress + exactly one Terminal), capability flags, and dependencies injected as typed context resources (Cwd, SessionEnv, Terminal, Params<T>, SessionFolder) via TypedExtensions instead of a god-object; a requirements DSL gates sibling-tool availability (bash/mod.rs lines 1490-1500).
3. LLM client — one enum (ApiBackend) over three wire protocols (chat_completions / responses / messages) with per-backend quirks encoded as methods (supports_native_schema, forwards_prompt_cache_key, default_max_request_bytes — xai-grok-sampling-types/src/types.rs lines 1046-1080); retry with jittered backoff + 429 classification + per-chunk idle timeout (xai-grok-sampler/src/retry.rs exports; ModelEntryConfig inference_idle_timeout_secs).
4. BYOK config schema — `[model.*]` / `[model_providers.*]` TOML with env_key (string or array), extra_headers, env_http_headers, query_params, command-based auth providers, and a documented credential-resolution order is directly transferable BYOK design (docs 11-custom-models.md; model_providers.rs). Signed requirements.toml fleet pinning maps to org-level model policy for the storytold org.

5. Headless-first CI ergonomics — `grok -p` with --output-format json (one object carrying text, stopReason, sessionId, num_turns, usage, per-model modelUsage, exact integer cost ticks `total_cost_usd_ticks`, and honesty flags like cost_is_partial / usage_is_incomplete), --tools allowlist, --max-turns, --allow/--deny rules, stable exit codes (0/1/130/143), stderr-for-humans / stdout-for-machines split (docs 14 lines 117-210). A GitHub Action should copy this output contract almost verbatim; the docs even show CI/CD code-review and pre-commit recipes (docs 14 lines 411-435).
6. Permission + sandbox layering — permission modes on top of allow/ask/deny glob rules on top of a kernel sandbox (Landlock/Seatbelt via nono; seccomp child-net blocking) on top of hooks that can rewrite/deny tool input (fail-open). For a GitHub Action: bypassPermissions + deny rules + read-only Landlock profile + optional deny hooks is a sane default posture; GitHub-hosted runners are already containers, but Landlock adds defense-in-depth on self-hosted runners.
7. Session persistence — resume/continue/fork by session id or title, per-prompt rewind checkpoints (FS snapshot + hunk delta + git HEAD/index), SQLite with filesystem-aware journal mode (WAL local / rollback NFS). Useful for an Action that reviews the same PR across repeated pushes.
8. Subagent architecture — task tool + coordinator actor + pure-resolution crate (precedence explicit > role > persona > parent), capability modes, depth limits; child sessions run isolated and report summaries back. Directly reusable for "review N files in parallel" fan-out across storytold repos.
9. Event discipline — typed tool notifications (BashExecutionComplete, FileRead, FileWritten, ScheduledTaskFired, PlanModeEntered... — xai-tool-runtime/src/notification.rs) and an ACP reducer mapping agent events to client-visible updates (xai-grok-pager/src/headless/reducer). A good skeleton for streaming GitHub check-run progress and PR comments.
10. Interop surface — ACP (agent-client-protocol 0.10.4, features unstable — Cargo.toml line 118) as the embedding protocol; plus AGENTS.md parsing (xai-grok-agent/src/prompt/agents_md.rs), skills discovery with .claude/.cursor compatibility (docs 08-skills.md), and Claude-compatible settings import (claude_import.rs in xai-grok-shell/src). An Action speaking ACP would interoperate with existing editors for free.
11. Do NOT copy for an Action: leader IPC, TUI/pager, plugin marketplace, voice, Mermaid rendering, Computer Hub, auto-updater, grok.com relay — all desktop/hosted-product concerns.

## 9. Open questions

- Licensing posture: Apache-2.0 first-party but "External contributions are not accepted" (CONTRIBUTING.md). Copying code requires Apache-2.0 attribution plus the tree's own notice chain (it already contains ports of openai/codex and sst/opencode code — THIRD-PARTY-NOTICES lines 16658+). For a new open storytold project, going upstream to openai/codex and sst/opencode directly (or writing fresh) is safer than lifting grok-build code; the *patterns* are unencumbered.
- No GitHub-native integration beyond export_github (commit+push helper): no PR review, Checks API, issue, or webhook code in-tree; VCS is git2/gix (Cargo.toml lines 178-179). A storytold Action must add its own GitHub layer (gh CLI or an octocrab-style crate — neither present here).
- The [patch.crates-io] async-openai fork (Cargo.toml lines 3-4) is private; if our engine needs Responses-API tweaks we must own our own fork.
- Token/cost accounting subtleties: num_turns counts main-agent rounds only (subagents excluded) and cost floats are omitted unless complete — an Action that budgets spend must parse usage_is_incomplete/cost_is_partial carefully (docs 14 lines 137-175).
