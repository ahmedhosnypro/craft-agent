## 1. What it is

DeepSeek Harness (`dsh`) is an open-source agent harness developed by DeepSeek AI, in developer preview with compatibility-breaking changes expected (README.md:5-13). Its distinguishing bet: an **everything-is-a-plugin** architecture powered by Cordis — "Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so each is replaceable from configuration" (docs/architecture.md:11).

- **Stack**: TypeScript pnpm-workspace monorepo, Node `^22.19 || >=24`, ESM-only; `dsh` runs from source via tsx ESM hook (`package.json:198` maps `"dsh": "node --import tsx/esm apps/cli/src/bin.ts"`; AGENTS.md:85-90,130). Vitest for tests, tsdown bundling, oxlint + lefthook, Python SDK under `python/`.
- **Layout**: `packages/` ~56 workspaces named `@deepseek-ai/dsh-*` (core agent/session, llm, shell, subprocess, ssh, terminal, sandbox, fs, lsp, web, subagent, mcp, webhook, workflow, jobs, guard, credentials, acp, sdk, host/client GUI …) per AGENTS.md:15-78; `apps/` cli, web, desktop, desktop-host; `native/` node addon; `vendor/` pinned Cordis; `benchmarks/` perf gates; `docs/` bilingual (en/zh) docs + generated catalogs; `website/` VitePress; `scripts/` verification gates.
- **License**: MIT, Copyright (c) 2026 DeepSeek (LICENSE); THIRD_PARTY_NOTICES.md discloses dependencies.
- **Usage**: `npx @deepseek-ai/dsh web` starts the Web UI at 127.0.0.1:3080 (README.md:19-27); from source `pnpm dsh --profile headless "task"` runs one task, needs DEEPSEEK_API_KEY (AGENTS.md:102).
- Run modes are **profiles** composed from **bundles**: `web`, `headless` (one-shot, no server), `sdk` (JSON-RPC server), `sdk-minimal`, `acp` (automation-only Agent Client Protocol server over JSON-RPC stdio) (docs/architecture.md:19,45; packages/acp/README.md). `dsh-base` is the shared first layer: model adapters, tools, persistence, sandbox and approval policy, settings, credentials, telemetry (docs/architecture.md:25).
- **Tool set** registered on `ctx.tools` (docs/tool-catalog.md rows): bash and pwsh, fs edit/read/read_image/write, glob/grep (packaged ripgrep spawned via ctx.subprocess), str_replace_editor, persistent terminals (terminal_open/read/send/…), lsp, subagent + interrupt_agent/list_agents/send_message, experimental agent teams, todo_write, plan mode (exit_plan_mode), job_kill/list/output, workflow, ralph, web_fetch/web_search, browser-use (stagehand_*), computer-use, session-query, goal, schedule, skill, MCP resources, plugin_manager, run_code (PTC runtime).
- **Quality culture**: unusually strict automated gates — per-file 100% coverage on packages (AGENTS.md:88), doc budgets enforced by word count (docs/AGENTS.md:48-58), session-format versioning with adjacent migrations, "model-visible means logged" runtime invariant (AGENTS.md:133, docs/architecture.md:125).

## 3. How it drives agents

- **Entry point**: one CLI, `dsh`, selecting a profile (docs/architecture.md:45). Application launches are locked down: "Only `dsh` profiles launch supported Node apps; package bins, demos, and public SDK argv escapes are forbidden" (AGENTS.md:11) — enforced by scripts/verify-application-entrypoints.ts (docs/architecture.md:47).
- **Agent loop** (packages/core/agent-loop, `ctx.agentLoop` implementing the `Agent` interface on `ctx.agents`): a **turn** is zero or more **steps**; a step is one model request plus the tools it calls. Event pipeline: turn/start → agent/pre-step (accept/reject/rewrite claimed input) → step/start → agent/request → prepareCall (route resolved before committing system+user messages; cancellation commits neither) → stream via llm/stream → agent/assistant-stream → tool/call → tools/pre-execute → tools/execute → tools/post-execute → tool/result → step/end → agent/turn-stopping → turn/end (docs/architecture.md:86-117).
- **Extension points are events**, not loop edits: "Plugins, not loop changes: new behavior goes on documented extension points; changing agent-loop requires updating docs/architecture.md" (AGENTS.md:137). Three event domains: durable session events, live `agent/*` events, capability events (`fs/*`, `tools/*`, `telemetry/*`) (docs/architecture.md:74-80).
- **Prompts**: `core/system-prompt` (`ctx.systemPrompt`) owns prompt-section and tool-schema assembly; the prompt travels only as `system/message` history, with provider-specific update modes like `systemPromptUpdate: in-history` for KV-cache-friendly mid-session prompt changes (docs/architecture.md table line 64; packages/llm/llm-deepseek/README.md:50).
- **Session log is the source of truth**: append-only `SessionEvent` log; `deriveMessages()` projects model history from it; fork, resume, transcripts, telemetry, persistence all derive from durable settlements (docs/architecture.md:119-127). JSONL with zstd compression, versioned files `session.vN.jsonl[.zstd]`, never renamed or deleted after commit, adjacent one-step migrations vN→vN+1 (docs/architecture.md:123).
- **Webhook → agent**: `dsh-webhook` (`ctx.webhookRuntime`) turns trusted external events into new Workspace Sessions via `register(rule)` / `dispatch(delivery)`; `WebhookSessionRequest` = {workspacePath, title, prompt, agentPreset, permissionPreset, model?} (packages/webhook/webhook/README.md). The rule's prompt is the only model-visible addition; the runtime adds no framing.
- **Automation surface**: the `acp` profile is an "automation-only server that exposes fresh harness agents to programmatic clients over JSON-RPC stdio… answer permission prompts; and cancel work without a human in the loop" (packages/acp/README.md). The Python SDK launches `dsh --profile sdk` with an explicit Harness home (docs/architecture.md:49; docs/user/guide/python-sdk.md).
- **Interop**: `packages/hooks/` bridges existing Claude Code and Codex `hooks.json` command hooks into dsh runs (packages/hooks/README.md).
- **DeepSeek targeting** is not hard-coded: the `deepseek-official` route is simply the default registered adapter on the provider-neutral `ctx.llm` seam; "Add a model provider → register its adapter on `ctx.llm`" (docs/architecture.md:143).

## 4. Model/provider config (BYOK)

- **Credential references, not secrets**: "The `credentials/` group lets configuration name secrets instead of embedding their values… `DEEPSEEK_API_KEY=… dsh` takes precedence for that run. Configuration files contain only credential names; local secret values remain readable only by the same OS user" (packages/credentials/README.md). Plugins take an `apiKeyEnv` field — an env-var NAME resolved per request through the credentials seam (packages/llm/llm-deepseek/README.md:38-55).
- **dsh-llm-deepseek** serves route `deepseek-official` over the DeepSeek **Messages API** at `https://api.deepseek.com/anthropic`. `baseURL`: explicit config → `$DEEPSEEK_BASE_URL` → official root (Messages-compatible gateways work). `reasoningEffort` off|low|high|max; default catalog: `deepseek-flash` (text+image, `systemPromptUpdate: in-history`) and `deepseek-v4-pro` (text-only), 1,000,000-token context; model ids pass through, so new DeepSeek models need no re-registration (packages/llm/llm-deepseek/README.md:50-83).
- **Stable failure codes** for provider errors: AUTH, QUOTA, RATE_LIMIT, CONTEXT_WINDOW_EXCEEDED, INVALID_REQUEST, SERVER, MISSING_CREDENTIAL, INVALID_CREDENTIAL (naming the reference to fix, never any part of the key) (packages/llm/llm-deepseek/README.md:117).
- **dsh-llm-pi-ai** is the multi-provider BYOK twin: routes for OpenAI, Anthropic, Azure OpenAI, AWS Bedrock, Google Vertex, Codex (OAuth), OpenRouter, self-hosted vLLM (openai-completions / openai-responses / anthropic-messages protocols), and **hand-declared gateways** — `api` + `baseURL` + `models` + `compat` switches (e.g. `thinkingFormat: deepseek`) with zero code changes (packages/llm/llm-pi-ai/README.md:12,40-105). Example config shows `openai: {apiKeyEnv: OPENAI_API_KEY, baseURL: …}` and a custom `acme-gateway` route.
- Stored sign-ins (OAuth or interactive key) live in the harness credential store at `llm-pi-ai/<provider id>` with cross-process refresh locking; per-route `apiKeyEnv` always wins (packages/llm/llm-pi-ai/README.md:93-95). pi-ai ambient discovery (`AZURE_OPENAI_API_KEY`, `AWS_PROFILE`, `~/.aws/credentials`) is consulted only after the harness seam (packages/llm/llm-pi-ai/README.md:219).
- **Swappability**: requests select a route with `GenerateOptions.provider`; both adapters mount together because route names don't collide; registering a route another adapter owns fails with DUPLICATE_ADAPTER (packages/llm/llm-pi-ai/README.md:34). Provider swaps keep the tool set: "pointing fs/subprocess providers at a remote sandbox moves Bash, PTY, and LSP with them" (docs/architecture.md:133).
- Model catalog fields per route/model: contextWindow, defaultMaxTokens, reasoningEfforts (renamable per gateway), requestImagePixelBudget/byte budgets, retryPolicy (provider-owned, executed by dsh-llm-retry at durable agent-step boundaries) (packages/llm/llm-pi-ai/README.md:84-105; packages/llm/README.md table).

## 5. Benchmarks & evaluation

- **BENCHMARK.md is a pointer, not a spec**: "Follow Get started with the Python SDK … run the `jsonrpc-agent` minimal variant. Use separate workspaces and session IDs for independent benchmark tasks" (BENCHMARK.md:3). External benchmark tasks are driven headlessly through the SDK profile.
- **benchmarks/ are performance gates, not coding-quality evals** — six measured user paths: active-stream-reconnect, agent-continuation, conversation-fold, long-session-browser, session-open, terminal-io (benchmarks/ dir listing). E.g. agent-continuation drives 100 turns and 800 real file reads through the shipped sdk-minimal profile; no browser, no network (benchmarks/agent-continuation/README.md:7).
- **Perf methodology** (benchmarks/AGENTS.md): one directory per measured user path (never mirror the package tree); `*.bench.ts` host cases, `*.bench.client.ts` client cases; compiled plain-Node workers under `benchmarks/.dsh-build/` — no TypeScript loader inside timed work; `fileParallelism: false`, `maxWorkers: 1` so measurements never share the CPU (vitest.bench.config.ts); five fresh-process samples in private `mkdtemp` roots; inputs synthesized from reviewed constants — "Never use recorded Sessions, user material, ambient repositories, or network services"; reviewed median budgets with an explicit CI time scale and variance headroom (e.g. 900 ms hosted expectation × 1.25 = 1,125 ms); raw + aggregate measurements must explain each verdict; env vars must never override budgets; exercise production entry points; record workload/timing/memory/calibration in an owning Agent Note.
- **Agentic-quality evaluation lives in the test pyramid instead** (AGENTS.md:86-99, docs/testing.md): `pnpm test` unit; `pnpm run test:e2e` real-API tests that **self-skip without DEEPSEEK_API_KEY**; `pnpm run test:snapshot` **keyless recorded-session replay through shipped profiles** (record with a key via `test:snapshot:record`, replay in CI with none); `test:expected` owner-local process expectations. Every non-trivial model-visible change updates a keyless recorded-session snapshot (AGENTS.md:155) — this is the reusable quality-eval idea: record once with tokens, gate forever without them.
- Real-API e2e cases also exist per adapter with opt-in env gates (`DEEPSEEK_IN_HISTORY_MODEL`, `DEEPSEEK_FLASH_E2E=1`, `DEEPSEEK_VISION_E2E=1`) (packages/llm/llm-deepseek/README.md:207).

## 6. CI / GitHub Actions usage

~20 workflows in .github/workflows (dir listing). The harness's own CI **does not run the agent against its repo**; it runs the test/gate suite plus two real-API e2e lanes. Notable patterns:

- **e2e.yml ("E2E real DeepSeek API")** — the model-key-in-CI reference: `pull_request` trigger with an explicit **SECURITY comment: NEVER change this trigger to `pull_request_target`** ("pull_request_target … runs in the BASE repo's context WITH secrets while still able to check out untrusted fork code — a textbook key-leak vector"); job-level `if:` skips fork PRs AND Dependabot PRs (Dependabot detected via PR AUTHOR, not github.actor); preflight **hard-fails if the secret is missing** so a self-skipping suite can't report false green; `DEEPSEEK_BASE_URL` pinned explicitly "so a stray repo-root .env can't redirect the run"; secret name DEEPSEEK_API_KEY_EXTERNAL mapped to the DEEPSEEK_API_KEY env the tests read; nightly cron `17 0 * * *` "off the top-of-hour cron stampede"; keep-only-newest concurrency (.github/workflows/e2e.yml:1-40).
- **pi-ai-provider-e2e.yml**: token-spending multi-provider e2e is `workflow_dispatch` ONLY ("no push, pull_request, schedule, or workflow_call trigger"), with model-id inputs; global `DSH_TELEMETRY_DISABLED: '1'` keeps CI off production telemetry (.github/workflows/pi-ai-provider-e2e.yml:1-25).
- **ci.yml**: pull_request-only; `contents: read` minimal permissions; cancel-superseded concurrency; **runner failover via repository variables** — `DSH_CI_FAILOVER_LINUX` unset/selfhosted/blacksmith retargets jobs between enterprise, in-house self-hosted, and Blacksmith pools with no PR-editable state (.github/workflows/ci.yml:1-50; .github/AGENTS.md).
- **ci-master.yml vs ci.yml split**: master-only platform checks, self-hosted standbys, manual runner benchmarks live in ci-master.yml "which listens to master pushes and workflow_dispatch, not pull_request; separating workflow triggers keeps master-only jobs out of PR check panels" (.github/AGENTS.md:3). Windows runs native pwsh on windows-* runners; Wine Windows-on-Linux lives only in ci-master (same file).
- **sandbox.yml**: keyless real-kernel confinement proofs (Landlock launcher built from native/system per leg) (.github/workflows/sandbox.yml:1-13).
- **weighted-approval.yml**: publishes weighted approval commit-statuses from a pinned-SHA trusted policy checkout (.github/workflows/weighted-approval.yml grep). issue-lifecycle.yml / issue-policy.yml manage issues; docs-pages.yml builds the website; release*.yml publish npm/Python/native artifacts.
- **No action.yml ships**: `find -maxdepth 2 -name action*.yml` returns nothing — dsh is not packaged as a reusable GitHub Action; automation reaches it via the ACP/SDK profiles or the webhook server (command output, 2026-10-10).

## 7. Reusable patterns for the storytold agentic GitHub Action

The highest-value find: **a complete, shipped reference for "GitHub event → agent session on a repo"** — docs/user/guide/github-review.md + apps/cli/config/examples/github-review/ (cordis.yml + github-ready-review-rule.mjs):

1. **GitHub webhook ingress** (dsh web + `--patch github-review/cordis.yml`): a second WebServer in an isolated realm on 127.0.0.1:3081, only `POST /github` registered, everything else 404; GitHub subscribes to Pull requests events with a high-entropy HMAC secret provided through the `DSH_GITHUB_WEBHOOK_SECRET` credential reference (github-review.md:8-64).
2. **The rule** (github-ready-review-rule.mjs): matches source/repository/event/action (`ready_for_review`), builds a `WebhookSessionRequest` with workspacePath, `agentPreset: standard`, `permissionPreset: read-only`, title `Review <repo>#<n>`, and a prompt that (a) pins the exact head SHA, (b) instructs re-fetching live PR metadata over the webhook snapshot, (c) forbids file/branch/PR/GitHub mutation, (d) **labels the event JSON as untrusted metadata, not instructions**, and (e) embeds it as `event_metadata_json` (rule file lines 40-65). Workspace routing maps repo full names to local checkouts; first delivery creates the Workspace, later ones reuse it (github-review.md:68-96).
3. **Delivery semantics worth copying**: HTTP 202 = "signature and JSON accepted, rule calls scheduled in memory", explicitly NOT "session created"; webhook runtime stores no delivery state; the inbound secret grants no outbound GitHub authority (github-review.md:98-102).
4. **BYOK done right**: config files carry only credential NAMES (`apiKeyEnv`), resolved per request through a credentials seam, with env override for one run and stable MISSING_CREDENTIAL/INVALID_CREDENTIAL failures (packages/credentials/README.md; llm-deepseek/llm-pi-ai READMEs). A new GitHub Action should take `api-key-env`/`base-url` inputs the same way — never raw keys — and support OpenAI-compatible gateways via a pi-ai-style provider table with per-route protocols and `compat` switches.
5. **Provider-neutral adapter seam**: one `ctx.llm` service; adapters register route names; per-request route selection; hand-declared gateway support without code. DeepSeek is just the default route, not an assumption (docs/architecture.md:143; packages/llm/README.md).
6. **Durable session log as the auditable transcript**: "Model-visible means logged" — everything the model saw is reconstructable from the log, enabling replay, fork, export (docs/architecture.md:119-127). For a GitHub Action, this is how you build PR-review comments, artifacts, and audit trails from one authoritative source; versioned append-only JSONL with adjacent migrations shows how to evolve the format without breaking old runs.
7. **Keyless replay evals**: record real sessions once (with a key), then `test:snapshot` replays them through shipped profiles with no key in CI (AGENTS.md:91-92,155). The storytold agent can record sessions against filmcraft/photocraft repos and gate behavior regressions in CI for free; real-API checks stay opt-in behind the e2e.yml secret model.
8. **CI security checklist to copy verbatim**: `pull_request` never `pull_request_target`; job-level fork/Dependabot skips; preflight hard-fail on missing secret; pin base URL against .env redirection; off-:00 cron; `contents: read` permissions; `DSH_TELEMETRY_DISABLED=1`-style global kill switch; PR-trigger vs master-trigger workflow split; failover via repository variables (.github/workflows/e2e.yml, ci.yml, .github/AGENTS.md).
9. **Sandbox before letting agents commit**: dsh-base ships sandbox and approval policy; `ctx.sandbox` backends confine spawned processes (Landlock proofs in sandbox.yml); read-only vs write permission presets gate review vs fix workflows (docs/architecture.md:25,153; github-review rule).
10. **Perf-gate discipline**: user-path-organized benchmarks with fresh-process sampling, synthetic reviewed constants, explicit budget semantics (benchmarks/AGENTS.md) — the harness-efficiency analog of the quality evals in item 7.
11. **Automation client shape**: the ACP JSON-RPC stdio server (create/resume sessions, answer permission prompts, cancel — no human) is the cleanest model for a GitHub Action runner driving dsh-style agents programmatically (packages/acp/README.md).

## 8. Open questions

- **Packaging**: dsh has no GitHub Action metadata (no action.yml found). For storytold, the decision is: wrap the SDK/headless profile in a composite Docker Action on a runner, or run a persistent webhook server (github-review pattern) with Actions only forwarding events. The repo offers evidence for both, no precedent for the first.
- **Upstream stability**: developer preview with explicit breaking-changes warning (README.md:13); session-format migrations are versioned but forward-only (AGENTS.md:7). Building directly on dsh packages means tracking a moving target; adopting its patterns is cheaper than depending on it.
- **pi-ai dependency risk**: the multi-provider adapter carries a local patch of `@earendil-works/pi-ai@0.85.1` fixing O(n²) tool-argument re-parsing, with a note to re-apply on every upgrade (packages/llm/llm-pi-ai/README.md:232) — a signal about pi-ai's maturity as a BYOK layer.
- **Cost control in CI**: provider-owned retryPolicy, token-meter, and image-offload budgets exist (packages/llm/README.md table) but nothing in-repo bounds per-Action-run spend; a storytold agent needs explicit run/token caps.
- **Write-path precedent**: the shipped GitHub example is deliberately read-only review; auto-commit-fix flows would need dsh's approval-policy and write presets worked out — no example exists in-repo.
- **Agentic coding quality**: no SWE-bench-style task benchmark ships; BENCHMARK.md only points at the SDK jsonrpc-agent variant for running external benchmark tasks. If storytold wants coding-quality evals, they must be built on that entry point (headless runs per task, separate workspaces/session IDs).
